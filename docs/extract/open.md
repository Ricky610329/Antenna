# 未解問題與未驗證宣稱

> 這份決定**新架構怎麼設計**。行號基準 commit `577d7ce`。

## O-1　冷啟動：新域 SM 比隨機差（「任意 spec」的擋路石）

**現況**：主 SM 在完全未見域選批 `P(勝隨機) = 21–26%`（K=30/60 皆然）——**比亂猜還糟**
（`analysis-10-sm-vs-physics.md` §5.2/§5.3）。現行對策只有一條**迴避規則**：
「開新域時不要用主 SM 挑候選」（已升 `decisions.md`），**沒有解法**。

**為什麼這是重寫的核心問題**：Ricky 想走到「人用自然語言描述 spec → 自動產生模擬檔」。
但**新 spec ＝ 新域**，每個新 spec 的前 N 批都會落在這個區間。解析與產檔反而是最容易的一段
（agent 現在就會改模擬設定達成橋接效果）；牆在這裡。

**已知可用的素材**：
- SM-blind 選席（R50 負片／橋接臂用 FPS，事後被 `analysis-10` 追認為正確）
- harvest warm-start（C-01 的「用既有量測資料庫挑起點」＝ +3.63 dB，但前提是**該域已有資料庫**）
- 影子 CNN 在未見域 K=30 有 71%（全域 ρ 僅 +0.078）——**小模型反而較穩**，但 CI 跨 0

**建議的第一個里程碑**（比 NL 介面更該先做）：拿**濾波器**當第一個新域，跑通
「blind 開局 → 域內 SM 上崗 → 過品質閘 → P(勝隨機) > 50%」。跑不通的話，NL 介面只是
把冷啟動問題包得更漂亮。

## O-2　模型驗收指標：ρ 不能用

`rank ρ` 與 top-K 選批效益**不等價甚至反向**（O-1 同出處）。diffsim 案例：修一個結構性物理 bug
讓 ρ 改善 **+124%**，而選批 `P(勝隨機)` 從 18%→17% **完全沒動**。

⇒ 新架構的模型上崗依據必須是**使用方式的指標**（`P(勝隨機)`，`sm_selection_audit.py` 口徑：
**平手算輸，所以完美預測器上限約 86%**，不是 100%）。ρ 只留作訓練期監控。

## O-3　協調層假設：共享檔案系統即匯流排

整套 claim／done／fail／stale 機制建立在三個前提上：
1. 所有 worker 看得到同一個目錄
2. `O_EXCL` 建檔在該檔案系統上**近似原子**
3. `mtime` 可信、可當心跳

換 NFS 照搬；**換 S3 前兩點就不成立**（無傳統的原子 create-if-not-exists 保證）。

**這是移植時真正要決策的一件事**，比選什麼框架重要。建議把這個假設壓縮進單一模組
（三個原語：`try_claim` / `liveness` / `atomic_write`），其上的 200 行認領/接管/熔斷邏輯就與
儲存後端無關——要上雲時只換那一個檔。

## O-4　harness 綁定只剩一項

agent 層約 **90% 與 harness 無關**（skill 是純 markdown runbook，判定邏輯已下沉到
`script/analyze.py`，工具直接印「→ 行動 ①~⑤」）。真正綁死的只有：

**`Monitor` ＝ 事件驅動的喚醒源**——讓「批次收檔」這個外部事件在人不在場時把 agent 叫醒。
整條 dispatch→watch→收檔喚醒→判讀→再 dispatch 的自續節奏靠它；已記錄兩次
「沒掛 watcher → 鏈斷睡死」事故（`docs/memory/feedback_failure_modes.md` 第七類）。

**好消息**：`dedust watch` 本來就是 blocking + exit code 契約的 CLI，所以綁定不在「偵測」而在
「誰來喚醒」。把終態事件寫成檔案（與既有的 NAS-as-bus 同構，不引入新假設），消費端就可以是
Monitor／cron／輪詢／人——`Monitor` 從唯一硬綁定降級為三種消費端之一。

其餘六項（PushNotification／背景執行／多模態 Read 目檢／skill 機制／memory 自動載入／hook）
抽象化難度低。

## O-5　未驗證宣稱：「換模型會得到同一份帳」

`methodology.md` §8.3 自陳這是**論證不是實驗結果**，沒做過「更換執行模型、重跑同一輪」的對照。
`methodology-divergences.md` S3 已降級為「設計意圖」。

**這條半天就能驗，而且回報很高**：選 2–3 個已收檔且已判讀的歷史批，快照後讓另一個模型／harness
從 `/takeover` 開始跑同一份 `/batch-cycle`，**遮蔽原判讀**（round 檔 §4），比對三層——

| 層 | 內容 | 預期 | 若不符代表 |
|---|---|---|---|
| L1 判定層 | `analyze batch` 印出的「→ 行動」被執行的結果 | 完全一致 | 弱模型化沒真的下沉，判定還在模型腦裡 |
| L2 記帳層 | round §3/§4 的數字、是否觸發公證/停批 | 一致 | runbook 有歧義分支 |
| L3 提問層 | 下一批假設、要不要開新輪、哪個異常值得追 | **預期不一致** | 若也一致，反而說明 agent 沒在提問（更壞的消息） |

零 HFSS 機時（用已收檔 store）。同時驗三件事：§8.3 的宣稱、本卷宗夠不夠讓新專案接手、
harness 中立化是否真的成立。
