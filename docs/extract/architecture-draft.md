# 新系統架構草案

> **讀者**：接手這套系統並長期使用的人（不一定參與過原專案）。
> **地位**：草案。每條標了證據等級與出處；標 `❓` 的是推論或設計意圖，**不是實驗結果**。
> 證據代碼見 [`claims.md`](claims.md)（C-NN）、[`ceilings.md`](ceilings.md)、[`open.md`](open.md)（O-N）。
> 行號基準 commit `577d7ce`。

## 0　這個系統要解決什麼問題

**問題形狀**（不限天線）：

1. 評估一個候選要跑**昂貴的模擬**（本專案：一筆 HFSS 約 100–200 秒）
2. 參數空間**大且離散**（25×25 二值遮罩 ＝ 2^625）
3. **規格由領域專家定**，而且會改（本專案規格改過三次，見 §4）
4. 目標不是「找到最佳解」，是「**在有限機時內找到夠好且可製造的解**」

**不適用**：模擬便宜（可以直接跑演化演算法）、參數連續且可微（用梯度）、規格固定不變。

**系統的一句話**：把「機時」當作稀缺資源來調度，用累積的量測資料庫決定下一批要燒什麼。

## 1　六層架構

```
┌ L5 代理層（LLM）      提問・選策略・判讀・裁決・寫工具        ← 外迴圈,可換 harness
├ L4 記帳層            紀錄真相源・公證・判準預註冊             ← 誠信保證,多策略下更重要
├ L3 判準層（spec）     量測口徑(凍結) / 評分層(可換)           ← 「任意 spec」的著力點
├ L2 策略層            N 個自走策略:取樣政策+變異規則+節奏      ← 本次架構的主要新增
├ L1 執行層            佇列・原子認領・容錯・跨機接管            ← 已有 ~500 行純通用實作
└ L0 資料層            (幾何宣告, 量測條件, 響應) + 去重 + era   ← 一級資產
```

**分層原則**：上層對下層只有**宣告**，沒有直接控制。L5 不直接派工（透過 L2 的策略註冊），
L2 不直接跑模擬（透過 L1 的佇列），L1 不知道 margin 是什麼（由 L3 注入 `evaluate_fn`）。

## 2　L0　資料層

### 2.1 一筆資料是什麼

```
條目 = (幾何宣告, 量測條件, 響應, 世代)
```

**四個欄位缺一不可**，理由都是踩過的坑：

- **幾何宣告**：不只是 bits。可製造性處理（菱形對角橋、挖空槽、像素尺寸）**是幾何宣告的一部分**，
  不是事後濾鏡。同一組 bits × 不同橋寬 ＝ **不同的量測對象，必須各自量**。
  ⚠ 這條是鐵則：`ceilings.md` §4 規律①（「事後修補」四個獨立案例全失敗，唯一成功的 R54 是把條件
  **前移到生成階段**）。把 overlay 當濾鏡會直接重演 p00 幻影事件（見 2.3）。
- **量測條件**：求解器設定（網格容差／掃頻法／逾時）必須**隨結果存證**。
  現行做法：輸入夾的 `hfss_setup.json` 整份複製進結果夾——「結果夾自帶這批用什麼設定量的，不靠人記」。
- **響應**：原始曲線，不是導出指標。導出指標會隨評分層改版（§4），原始曲線不會。
- **世代（era）**：見 2.3。

### 2.2 去重

內容 hash 即檔名（本專案 `SampleStore`，76 行，sha1 前 16 碼）。一筆一檔的好處：O(1) append、
天然去重、壞檔只損一筆、無 pickle 安全問題。

**發車前的全歷史查重是獨立的一道閘**（不是資料層的事）：候選送模擬前跨全部歷史比對，
重複即擋。蓄意重複（公證重測）用 `kind` 欄豁免。

### 2.3 ⭐ 世代（era）是一等公民 —— 長期使用最容易被忽略的一條

**事件**：本專案 2026-08-13 發現舊幾何（p00）的零厚度對角接觸是**數值幻影**，量出來的值
不可作實物預測。換代到 p01 後，`records_dual.json` 有**四個紀錄鍵被永久標記 `era: p00(凍結)`**，
不可與新代比較（C-24）。

**對長期使用的意義**：模擬器、幾何底板、求解器版本都會換。換代之後，**歷史資料不是變錯，是變成
不可比**。若系統沒有把 era 做成一等欄位，三年後接手的人會拿跨代數字做決策而不自知。

**設計要求**：
- 每筆資料帶 era 標籤
- 跨 era 比較預設**禁止**，要比必須顯性重測
- 紀錄榜依 era 分帳，舊代凍結保留（不刪，那是歷史證據）

### 2.4 儲存後端與協調語義要分開

本專案把「NAS 共享目錄」同時當成**儲存**和**協調匯流排**。這兩件事的需求不同：

- 儲存：只要能讀寫、能備份
- 協調：需要 `O_EXCL` 近似原子 + `mtime` 可信當心跳

換 NFS 兩者照搬；**換 S3 協調語義就不成立**（無傳統的原子 create-if-not-exists 保證）。

⇒ **把協調假設壓縮進單一模組**，只暴露三個原語：`try_claim` / `liveness` / `atomic_write`。
其上的認領/接管/熔斷邏輯就與後端無關，要上雲只換那一個檔（O-3）。

### 2.5 備份紀律（不可省）

量測資料是**唯一重跑不回來的東西**（程式有 git、模型能重訓、圖能重畫）。本專案：一筆約 100 秒、
六萬多筆 ≈ 兩千小時機時。

鐵則：增量、只讀來源、**永不用鏡像模式**（會刪掉目的地多出來的檔）、跑完對帳。
本專案實際靠這條保住了 417 個來源端已被清掉的權重檔。

## 3　L1　執行層

### 3.1 職責與無知

執行層**只認得字串**：`{input, store, prio, config?}`。它不知道模擬器是什麼、margin 怎麼算。

介面：

```
run_batch(manifest, work_dir, *, sim_factory, evaluate_fn, results_path, fault_knobs)
    sim_factory() -> 有 open/start/__call__/end/quit 五個方法的物件
    evaluate_fn(raw_response) -> dict     # 寫進結果的欄位
```

### 3.2 必須有的容錯（每一條都是事故的產物）

| 機制 | 防什麼 |
|---|---|
| 原子認領（`O_EXCL` 建 claim 檔） | 多台同時抓同一個工作 |
| 心跳＋stale 接管（看結果檔 mtime） | 機器整台死掉 |
| 單筆看門狗（逾時殺求解器） | 單一壞幾何卡死整批 |
| 連敗熔斷 → 冷卻 → 重開 → 判死三層 | 求解器崩潰後的雪崩 |
| `.fail` 記機器名單、別台自動接管 | 單機環境問題 vs 真毒樣本的區分 |
| 可中斷續跑（進度全在結果檔） | 中斷、讓位、接管都不損失 |
| 工作目錄跑完即刪 | **磁碟塞爆**（本專案實際發生：78 個暫存吃光系統碟，引發連環求解器例外，重開機是假好轉） |
| 低優先工作立即讓位 | 背景填充不擋正式工作 |

**設計要點**：冪等是地基。進度全部落在結果檔，所以中斷/讓位/接管都只需重讀該檔，
不需要額外的狀態機。

### 3.3 部署紀律

改動執行層程式後：推送 → **逐台拉取 + 重啟 worker** → 首筆冒煙 + 查佇列。
「只拉取不重啟＝跑舊程式」在本專案犯過兩次。

## 4　L3　判準層（先講這層，因為 L2 依賴它）

### 4.1 ⭐ 量測口徑 vs 評分層分離

**這是本專案最被低估的資產**，也是「任意 spec」唯一已被驗證的著力點。

```
量測口徑（凍結）：響應怎麼量、頻點集合怎麼取 → 換代要走公證流程
評分層（可換）  ：門檻是多少、哪幾軸進 min → 專家改規格時只動這層
```

**實證**：本專案的規格由領域專家改過（帶內門檻放寬 2 dB、阻帶放寬 5 dB、帶外退場），
**不必重量任何資料**，缺口從 6.1 → 3.05 dB（C-23）。實作上評分層是四個偏移量與一個 min 組合。

⇒ 新系統要把 spec 做成一等物件：

```
Spec = (labels, 量測口徑[凍結], 評分函式[可換])
```

「自然語言 spec → 自動產生模擬檔」這條路，**產出的應該是這個物件**（或它的序列化），
下游一行不改。解析與產檔反而是最容易的一段——牆在冷啟動（§6）。

### 4.2 判準預註冊

一個實驗的通過條件**必須在看到結果前寫下**。這是誠信保證的核心，不是形式。
本專案的載體是 round 檔 §1，發車前寫死。

### 4.3 判準的方向自證

判準函式應該自帶方向檢查（例如「反射類的中心必須低於邊帶、傳輸類必須高於」），
配錯直接失敗而不是靜默算出無意義的數字。本專案在判準函式裡做了這件事，擋掉過真實的配錯。

## 5　L2　策略層（本次架構的主要新增）

### 5.1 策略的三要素

```
策略 = 取樣政策（怎麼從資料庫抓起點）
     + 變異規則（怎麼從起點生新候選）
     + 節奏（自己什麼時候跑，不等別人）
```

本專案已經有**60+ 個硬編實例**（`select_*` 家族約 4000 行）。**那些程式碼不要搬，但要挖它們的分類法**：

| 取樣政策（已驗證存在的） | 變異規則（已驗證存在的） |
|---|---|
| 依既有量測值排序取前 K | 鄰域翻轉 d=1..6 |
| 遠域家族補位（互距 ≥ N bits） | 雜交（割線拼接） |
| 代理模型 LCB（mean − std） | 對稱化生成 |
| 代理模型分歧（std 最大） | 結構算子（開縫／橋接／組塊增刪） |
| **完全不看模型的隨機**（對照臂） | 嫁接（跨家族移植） |
| 血統多樣性稅（限制單一根的佔比） | 梯度反傳生成 |

### 5.2 非同步，但**共享狀態**

策略各自照自己節奏，**不等別人的模擬結果**；但**必須讀得到別人已完成的結果**。

理由：最大的單一槓桿是「用既有量測資料庫挑起點」（C-01：+3.63 dB vs 零演算法對照臂，
比局部開採的 +2.08 還大）。策略若各用各的資料，等於放棄這個複利。

⇒ 措辭要定死：**非同步的是執行，不是狀態**。

### 5.3 ⭐ 每個策略常駐自帶 blind 對照臂

**這是架構級的要求，不是實驗設計。**

多策略並行會殺掉歸因——本專案能算出「選拔 +3.63／開採 +2.08」是因為當時同一批裡有一個
**零演算法對照臂**。十個策略同時跑，這種拆帳做不出來。

解法：每個策略固定切出一定比例給「完全不看模型的隨機抽樣」，**比例不得為 0**。
這樣任何時刻都能回答「這個策略比亂猜好多少」，不必另外設計實驗。

本專案已有這個機制的雛形（補池的三臂配額，其中一臂完全不經模型）；新系統要把它從
「某個管線的設計」升格為「所有策略的合約」。

### 5.4 多樣性從策略池湧現，不必在單一策略內硬塞

本專案的多樣性機制全都塞在單一管線裡：反自餵、反馬太四機制、根多樣性稅、相似度稅、
選中者互距下限。**這些存在本身就證明了多樣性崩潰是真問題**（純模型導向會自我強化）。

多策略架構下，**取樣政策不同的策略同時跑，天然就分散**。單一策略內只需保留最便宜的那道（去重），
其餘的稅可以拆掉，每個策略會簡單很多。

### 5.5 策略的生死

需要顯性的 lifecycle：**誰決定某策略該停、憑什麼指標、資源怎麼重分配**。

- 指標：該策略的 blind 對照臂比值（5.3）＋ 對紀錄的貢獻率
- 判決：由 L5（人或代理）在**判決邊界**做，不由策略自己做
- 停滯：連續 N 個週期無推進時升級處理（診斷 → 換分布 → 證天花板 → 帶帳本升級給人）

⚠ **不要讓策略自己決定生死**——會演化成只保留短期命中率高的，多樣性崩潰。

## 6　冷啟動：新 spec 進來時怎麼辦（O-1）

**已知事實**：代理模型在**完全沒見過的域**選批，勝過隨機的機率只有 **21–26%**——
**比亂猜還糟**（C-07，K=30/60 皆然）。而且 `rank ρ` 與選批效益**不等價甚至反向**（C-08）。

這是「任意 spec」的擋路石，本專案**沒有解，只有迴避規則**。

**新架構的處理**（比舊系統好，因為架構天生帶對照臂）：

```
新域第 1 批   ：強制 blind（隨機／文法／對稱化）。模型一律不得參與候選挑選
域內模型上崗前：樣本數門檻 N（從歷史開線資料回推）
上崗閘        ：排序相關性 ≥ 門檻 且 命中率統計檢定顯著；不過 → 該輪降級為 blind
上崗後驗收    ：用「勝過隨機的機率」，不是相關係數
```

5.3 的 blind 對照臂讓這件事**自動成立**——策略池裡永遠有 blind 在跑，新域不需要特別處理。

**建議的第一個里程碑**：拿一個新元件類型當新域，跑通「blind 開局 → 模型上崗 → 勝過隨機 > 50%」。
跑不通的話，自然語言 spec 介面只是把冷啟動問題包得更漂亮。

## 7　L4　記帳層

多策略自動跑之下，這層**只會更重要**——否則十個策略會互相污染彼此的「紀錄」。

| 機制 | 內容 |
|---|---|
| 單一真相源 | 紀錄與門檻放在一個機器可讀的檔，程式讀它、不讓人憑記憶抄數字 |
| 公證鐵則 | 紀錄級宣稱必須重複量測確認；跨機時取保守值 |
| **迴圈不自己加冕** | 自動迴圈發現破紀錄候選 → 只能寫進「待審」，**不得直接改紀錄**。換王由人或判決流程定 |
| 假象攔截要記帳 | 沒過公證的候選也要留紀錄（本專案靠這條攔下過假王：單次 −5.49 → 跨機 −5.83） |
| 門檻只能因公證而動 | 禁止為了製造進度而降門檻 |
| 負結果是一等產物 | 失敗與被推翻的結論要保留，否則只有成功案例進入敘事 |

## 8　L5　代理層（LLM）

### 8.1 位置：外迴圈，不在內迴圈

**證據**：本專案的無人值守迴圈明寫「迴圈裡沒有 LLM」，而現任最佳解正是它產出的（C-10）。

| 代理負責 | 代理明確不負責 |
|---|---|
| 提出可驗證的假設 | **判定**（門檻、通過與否 → 寫進程式） |
| 選策略、配資源 | 改寫成功標準 |
| 判讀結果、寫下一輪 | 宣告紀錄成立（只能觸發驗證） |
| 寫工具、改基礎設施 | 決定研究方向的價值 |

### 8.2 判定要下沉到程式（「弱模型化」）

理由：**模型會換版、會漂移，但程式裡的判準不會**。做法：分析工具直接印出「→ 建議行動 ①②③」，
代理照抄執行，在分支點選路。

⚠ 但要誠實：這條的完整宣稱是「換一個模型接手會得到同一份帳」，而**本專案自陳這是設計意圖、
沒做過對照實驗**（C-11）。新系統若要主張這一點，必須先做那個實驗（見 §10）。

### 8.3 harness 中立

代理層約 90% 與 harness 無關（runbook 是純文字、判定在程式裡）。真正的綁定只有一項：
**事件驅動的喚醒源**——讓「批次收檔」這個外部事件在人不在場時把代理叫醒。

⇒ 設計：收檔偵測寫成獨立 CLI（blocking + 退出碼契約），終態時**寫一筆事件檔**。
消費端可以是任何 harness 的背景監看、cron、輪詢、或人。喚醒機制從「唯一硬綁定」降級為
「三種消費端之一」。

⚠ **發車必須伴隨掛偵測**：本專案記錄過兩次「派工了但沒掛監看 → 鏈斷睡死」。
兩者要在同一個動作裡完成。

## 9　跨層鐵則（違反會系統性出錯）

這六條是從失敗歸納的，不是偏好：

1. **約束在生成端表達，不做事後修補。** 事後對稱化、斷角清潔、可製造化清潔、零點手術——
   四個獨立案例全失敗（代價中位到 −17 dB）；唯一成功的是把可製造性條件前移到候選生成階段
   （稅 −0.07，≲網格噪音）。
2. **驗收用「使用方式」的指標，不用「看起來合理」的指標。** 相關係數改善 124% 而選批效益
   完全沒動的案例真實存在。
3. **離線考 ≠ 實戰考**（本專案三度應驗）。模型上崗要用實戰口徑重考。
4. **代理模型的價值是粗篩，不是細排。** 盆地內細排零加值已被對照臂證實。
5. **跨世代不可比。** 儀器換代後歷史數字凍結，要比就重測。
6. **量測資料是唯一重跑不回來的東西。** 備份用增量、只讀、零刪除、跑完對帳。
