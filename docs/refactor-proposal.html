0讀完論文後，先確立兩個事實（取代先前的「待確認」）

① 命名陷阱：論文的 GEN ≠ 程式碼的 SigmoidGEN
  • 論文 GEN（Gradient Estimation Network，梯度估計網路）= 代理模型（程式碼 OldSM/HFSSNet）。
  • 程式碼 SigmoidGEN = 生成器 G（名字裡 GEN 只是 Generator 縮寫，與論文 GEN 同名異義）。
  • → 重構命名要避開撞名：生成器叫 G、代理叫「代理/Surrogate」或註明（論文 GEN）。
✅ 已確認（原 Q1）：ACP 與 rollback 是兩個獨立機制，應該分離
論文第 3.2 節定義的 ACP（Adaptive Cyclical Policy，自適應循環策略）= AdaptiveCyclicalScheduler，只含「主動式高原偵測 + 自適應重啟 + lr/tau 雙耦合退火」，只動 lr/tau、不碰權重。 rollback（載回歷史最佳 + 重訓代理）是主迴圈層級的獨立機制，用另一套獨立 patience（TEMP.early_stop(..., config['patience']=10)）。
→ 本提案把「排程」與「回滾」拆成兩塊（B 與 C），論文佐證方向正確。注意 ACP 本身已是現成類別，重構時是「被持有/被呼叫」，不需重寫。

1為什麼要重構？

現況：train_single.py 與 train_dual.py 各是一支由上到下的單體腳本，把設定、元件建立、整個訓練迴圈、回滾、線上訓練代理、繪圖、通知全混在一起；兩支約 95% 重複，只差「模擬器 / 響應 / 損失 / 饋電塊 / 回滾時的取樣」。
⇩ 問題
  • 改一個邏輯要同時改兩支，易不一致（已抓到 dual 的 island_suppression 鍵名 bug）。
  • 迴圈、回滾、排程、繪圖耦合，難以單獨測試或替換。
  • 要加新埠／新回滾策略／新排程，幾乎得整支複製。

2提案架構：三層職責分離

train_single.py/train_dual.py 最後只剩「建設定 → 組裝 → 跑」約 10 行。

A元件整合類別 DesignPipeline（名稱待定）

把各組件整合並提供原子操作。不跑迴圈，只提供「做一件事」的能力。

  • 持有：g(SigmoidGEN + Adam + ACP 排程器)、surrogate(OldSM＝論文 GEN)、sim(Single/DualPortSimulator)、responses(目標+loss hook)、static_feeds(lower/upper)、online_dataset、record(TEMP)、config。
  • 方法：generate()、simulate(pattern)(含去重)、train_surrogate_one(...)、train_surrogate_batch(...)、update_g(pattern)、save()/load()。

B訓練迴圈 Trainer（驅動 ACP 排程器）

負責 epoch 迴圈的編排：每步呼叫 pipeline 的原子操作、推進 ACP 排程器（AdaptiveCyclicalScheduler，lr/tau）、處理繪圖/記錄/通知。回滾決策委派給下面的 C。

  • run()：主迴圈。
  • ACP 排程器是現成的，這層只是「在對的時機呼叫它的 step(real_loss)」。

C回滾機制 RollbackPolicy（論文確認獨立）

「停滯偵測 → 回滾 G 到歷史最佳 → 重訓代理」這套策略，獨立成可抽換物件。

  • should_trigger(record, patience) → 包住 Record.early_stop（主迴圈那套獨立 patience）。
  • apply(pipeline) → 找最佳 epoch → 回滾 G(g.change(best, load=True)) → 重訓代理。
  • single/dual 差異收斂在這：single 用整個 online_dataset；dual 用 filter(upper=平均loss)（後者較接近論文 DLF）。

關係圖（注意命名已對齊論文）

# train_single.py / train_dual.py 只剩這樣：
cfg      = SingleConfig()           # 或 DualConfig()
pipeline = DesignPipeline(cfg)   # A：持有 G / 代理(論文GEN) / SIM / ACP排程器 / 資料
trainer  = Trainer(pipeline, rollback=RollbackPolicy(cfg.refit))  # B + C
trainer.run()

# Trainer ──uses──▶ DesignPipeline ──holds──▶ G / 代理(論文GEN) / SIM / ACP排程器 / Data
# Trainer ──每步呼叫──▶ ACP.step(real_loss)        (只調 lr/tau，不碰權重)
# Trainer ──委派──▶ RollbackPolicy ──作用於──▶ DesignPipeline  (回滾 G + 重訓代理)

3tau：唯一橫跨「排程 ↔ 模型」的耦合

重構想讓「ACP/排程」與「模型」各自獨立開發，但有一個參數 tau（二值化溫度）橫跨兩者，必須先處理乾淨。

tau 是什麼（先澄清）

  • 不是模型權重：現行 SigmoidGEN 的 tau 不是 nn.Parameter、不在 model 的 state_dict；它是排程純量，存在 ACP（AdaptiveCyclicalScheduler）的 state（current_temp）裡。
  • （被移除的 GumbelSigmoidGEN 曾把 tau 設成可學習參數，但主路徑 SigmoidGEN 沒有。）
⚠ tau 同時影響「前向」與「反向」→ 它真的耦合了 ACP 與模型
  • 前向：binarization 用 steepness = 1/tau 控制 sigmoid 陡峭度（tau 小→輸出趨近硬 0/1）。
  • 反向：STE 梯度也被 1/tau 縮放 → tau 改變流回 G 權重的梯度大小。

而且目前是隱性全域變數耦合：

ACP.step() ──寫──▶ AntennaPattern.tau (class 全域) ──讀──▶ binarization()
# ACP 偷偷改全域、模型 forward 偷偷讀 → 「改 ACP 卻悄悄改了模型行為」

建議：把隱性全域改成「一個顯式純量接縫」

  1. lr 與 tau 都留在 ACP、不要拆開——論文核心就是「lr/tau 雙耦合退火」，ACP 是「同時產出 (lr, tau)」的單一排程源。
  2. tau 變成 G 的顯式輸入：G.forward(spec, tau) / binarization(x, tau)，移除 AntennaPattern.tau 全域副作用。
  3. 「排程 ↔ 模型」的契約濃縮成一個純量 tau。
Trainer 每個 epoch:
   lr, tau = acp.step(real_loss)         # ACP 唯一負責「怎麼排程」
   pattern = pipeline.generate(tau=tau)  # 模型唯一負責 (spec, tau) -> pattern
   pipeline.update_g(pattern, tau=tau)

之後的「使用模式」

你想改動哪些模組對 tau 的責任
改進 ACP / rollbackACP、RollbackPolicy、Trainer你決定「tau 怎麼產生/退火/重啟」。模型不用碰。
改進模型 GSigmoidGEN（或換新網路）只要保證契約 forward(spec, tau) → pattern；測試時給固定 tau（如 1.0）即可單獨跑。
心裡要有數的 caveat：兩種耦合不一樣
程式碼耦合可消除（變顯式介面），但演算法耦合消不掉、也不該消——改 ACP 的 tau 排程，即使模型架構不變，模型的訓練動態與最終結果仍會變（梯度被 1/tau 縮放），這是論文方法本質。所以「獨立」精確的意思是：模組程式碼互不侵入；只有 tau 這個執行期數值跨越接縫。可分開「開發/測試」，但「調參時 ACP 與模型仍互相影響」要知道。

5設計決策（已定案，皆採下方標「推薦」選項）

✅ 全部已定案並實作

Q2　整合類別要不要自己跑迴圈？
(a) 只「持有元件 + 原子操作」，迴圈交給 Trainer 推薦。　(b) 自己也跑迴圈（把 Trainer 併進去，但又耦合回來）。
Q3　single / dual 如何處理？
(a) 單一 pipeline + SingleConfig/DualConfig 驅動 推薦。　(b) 兩個薄子類別。
Q4　命名要不要對齊論文？（建議「是」）
建議：生成器叫 G、代理叫 Surrogate（或保留 OldSM 但註明＝論文 GEN）、排程叫 ACP、回滾叫 RollbackPolicy。務必避免再用 GEN 一詞指生成器，以免與論文撞名。
Q5　行為要「完全一致」還是「可順便改進」？
(a) 純重構、數值等價 推薦先這樣。　(b) 重構同時順手修（例如 dual 的 island 鍵名 bug）——但會讓「重構是否正確」較難判定。
Q6　遷移方式？
(a) 新架構放新檔（antenna/pipeline.py 等），舊腳本先不動，驗證等價後再切 推薦。　(b) 一次性原地替換（風險高）。
Q7（新）　DLF 落差：要不要在重構時補成論文版本？
論文 DLF＝「每輪用累計平均重新過濾整個 buffer」；現有 train_single 只做「real_loss<平均才寫入」（論文點名的對照基準）。
(a) 純重構先原樣保留現有行為，DLF 另案處理 推薦。　(b) 重構同時把 DLF 補成論文版（屬「行為改進」，需配 Q5-b）。

7風險與保護

  • HFSS 慢 + 隨機 → 難端到端回歸：Mock 模擬器 + 固定種子 + 純函式單元測試。
  • app.py 依賴序列化格式 → 不可改 Record/DataManager/Data 結構。
  • 命名撞名 → 全程避免用 GEN 指生成器；統一「G＝生成器、代理＝論文 GEN」。
  • 行為漂移 → 以基準數列逐項比對；先做「純重構（Q5-a）」最易判定對錯。
  • 範圍蔓延 → 重構與修 bug／補 DLF 分開 commit。
