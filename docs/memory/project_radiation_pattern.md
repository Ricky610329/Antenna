要把 radiation pattern（gain vs 角度，固定 28GHz、phi 0°/90°）納入閉迴路當 loss。刻意與 S11/Gain 主路徑解耦、零侵入。

**已做（資料萃取）**：`SinglePortRadSimulator`（`antenna/patch/patch_simulator/single_port_rad.py`，繼承 `SinglePortSimulator`）。求解後多匯出 `dB(GainTotal)` vs Theta、Freq=28GHz、Phi∈{0,90}。回傳值與父類別**完全相同**（只 S11/Gain，不塞方向圖避免 criterion zip 對齊錯位）；方向圖寫 CSV + `self.last_radiation`。驗證腳本 `script/verify_radiation.py`（正式機跑），結構測試 `tests/test_radiation_simulator.py`。**未接 build_simulator**，train.py 不用它。

**SM/loss 已實作（Stage 1-2，2026-06-19，golden 零漂移已驗）**：
- **rad head（`antenna/models/surrogates.py`）**：`HFSSNet` 的 `fc_patch`（freq）**原封不動**，rad head 從 `fc_patch[:-1]`（末層 Linear 前的 64 維共用 backbone）分叉 → `forward_rad`。`head_rad` 在 `fc_patch` 之後才建 → 從零建構 freq 參數 RNG 序列不變、`fc_patch` 名稱不動 → golden 零漂移 + 舊 `sm.pth` 零 remap（測試 `test_rad_head_does_not_perturb_freq_params` 直接驗）。`SurrogateModel.train_one_data_rad`/`rad_predict` 為對應入口。
- **trunk 改回「預設凍」（2026-06-19 二次修正，因 NaN 爆炸）**：原本使用者選「先不凍、求簡單」，結果正式機跑 `single_sc_rad` 時——隨機 rad 頭 + trunk 不凍 + 激進單筆擬合 + 極端 dB target——把共用 backbone 帶歪 → 下一個 epoch 的 `train_one_data`(S11/Gain) 預測爆成 1e6 → MseLossBackward 回 NaN、整個 run 掛掉。修法三層：①`train_one_data_rad(freeze_trunk=True)` 預設凍（只更新 head_rad，Ranger 對 grad=None 自動跳過）②`run_training` 清理 rad target（nan_to_num + clamp 到 `_RAD_DB_FLOOR/CEIL` ±60dB，因深零點 dB 可能 -inf）③SM 三個訓練入口加 NaN 防護網（loss 非有限就跳過該步）。config `radiation.freeze_trunk`（預設 true）可關。測試 test_rad_freeze_trunk_protects_backbone / test_radiation_loop_survives_extreme_targets / test_train_one_data_nan_guard。
- **關鍵洞見（仍成立）**：拆最後一層成多頭數值上是 **no-op**（`Linear(64,2N)`≡兩個`Linear(64,N)`）→ **S11/Gain 不拆**。
- **rad head 改平滑 cosine 基底頭（2026-06-22，解鋸齒）**：起因＝使用者看 TB `radiation/gain_vs_angle` 發現「SM(pred) 實線鋸齒」（HFSS 真值虛線平滑；查 code 確認鋸齒是 SM 預測、非 CSV/畫圖，CSV 萃取+`monitor.py` argsort 都對）。根因（config 自己寫過）：`head_rad` 是「凍 trunk 下的單層 `Linear(64→n_phi·n_theta)`」，無平滑先驗 + 擬不到 0.1（撞 `sm_max_epoch`）→ 吐沒擬合完的鋸齒殘差。修法＝方向 A（使用者選，**不碰 loss**）：`head_rad` 改吐 K=`n_basis`（預設16）個 cosine 係數 → 乘固定基底 `B(K,n_theta)` 展開（`pred=coeffs@B`）→ band-limited、**結構上必平滑**、只擬 K 個數收斂快。`B` 不可訓 buffer、`torch.cos/arange` 建（不吃 RNG→golden 零漂移）；`HFSSNet.set_rad_theta(theta)` 依實際 HFSS θ 網格（整 run 固定）逐欄重建→對位正確、HFSS 匯出序未排序也 OK；`run_training` 第一次拿到 rad_theta 時呼叫。config `radiation.n_basis`，串 `build_surrogate→MLPSurrogate→HFSSNet(rad_n_basis)`。⚠ head 形狀變 → 舊 rad-run `sm.pth` 不能續跑（freq-only checkpoint 不受影響）。測試 `test_rad_head_basis_is_band_limited`(K=1→沿θ恆常數)/`test_set_rad_theta_rebuilds_basis_and_aligns`/`test_rad_n_basis_clamped_to_n_theta`/`test_config_accepts_n_basis`。隨機初始實測排序後 TV 4.94 vs 裸 Linear 17.16（≈3.5×平滑）。
- **loss `beam_coverage_loss`（`antenna/losses.py`，測試 `test_beam_coverage_loss.py`）**：①`mean(relu((G0−floor_db) − G[θ∈窗]))` + boresight_weight·②`mean(relu(G[θ] − G0))` + flatness_weight·③`mean((G[θ∈窗]−G0)^2)`，G0=rad_pred[θ≈0]。相對 boresight、自我歸一化 → 方向圖**不需**寫 target 曲線；boresight 絕對增益交給既有 `Gain` target。窗/floor（**±45°**/3dB）是學長後續討論定的規格（原 ±55，已 commit d69482a），仍可調。
- **③ flatness 項（2026-06-23，opt-in，使用者要「±45 高且平整」）**：`flatness_weight`（預設 0＝完全不影響、golden 安全）。①是 hinge（只罰掉超過 floor 的、帶內 0 梯度＝**容忍** ripple）；③對任何偏離 G0 都給梯度（雙邊平方）＝**主動壓平**到 boresight 準位、順帶拉高窗內。串 `radiation.flatness_weight`→`training.py`→`beam_coverage_loss`。**對照實驗矩陣（都 base=single_sc_rad、各一變因，未跑、需正式機）**：`single_sc_rad`(floor_db=3 baseline)、`single_sc_rad_flat15`(floor_db 1.5)、`single_sc_rad_flat10`(floor_db 1.0)、`single_sc_rad_flatloss`(flatness_weight 0.5)。物理張力：平頂波束峰值天生較低，「又平又高」會互相拉扯，floor_db/flatness_weight 是取捨旋鈕。測試 test_flatness_weight_zero_is_noop / _penalizes_deviation_from_boresight / _zero_for_perfect_flat_top。改 loss 前依 [[feedback_discuss_before_loss_change]] 已先討論取得同意。
- **訓練接法（`run_training`，`rad_on` 閘住）**：`build_simulator` 開啟換 `SinglePortRadSimulator`；每筆真實模擬後讀 `simulator.last_radiation`、`train_one_data_rad` 訓 rad head；過 `warmup_epochs` 後把 beam loss 加進 GEN loss。`rad_on=False`→全不執行（golden 零漂移）。config 範例 `configs/single_sc_rad.yaml`。
- **冷啟動暖身（2026-06-19 修「HFSS 卡住」根因）**：rad 版 SM 多 `head_rad`，但 trunk/freq head 與 `old_sm.pth` **同名同形** → `pre_load_model(path, strict=False)` **部分載入**（共用層暖啟動、`head_rad` 維持隨機）。`prepare_models` 在 `cfg.radiation.enable` 時自動帶 `strict=False`；single_sc_rad.yaml 用 `pretrained: old_sm.pth`。
- **⚠ optimizer 必須一起暖啟動（2026-06-20 真正的 NaN 病根）**：strict=False 起初「跳過 optimizer」→ **冷 optimizer + 暖權重**讓 `train_one_data`（S11/Gain！）在 **epoch 1** 第一步就過衝、3 步發散爆 inf（實測同一筆：warm `2136→2079` 緩降 vs cold `2136→90→4.9e6→inf`）。NaN 防護網只擋 crash、擋不住前 3 步的灌爆 → SM 廢掉、gen_loss 1e37、GEN 退化成固定 pattern 撞快取空轉。**真正的修法＝`pre_load_model` 的 `_warm_start_optimizer`**：把預訓練檔 per-param 狀態依「參數順序」對位灌進現有 optimizer（head_rad 在序末、保持新鮮）。前提是 head 接在原參數序之後（golden-safe 建構保證）。教訓：先前「凍 trunk/清 target/NaN 防護」三層都診斷錯方向——病根是冷 optimizer，不是 rad 污染 trunk。測試 test_pre_load_partial_warm_starts_optimizer。
  - **踩過的雷**：當初以為「多 head 載不進舊檔」→ 拿掉 pretrained 只留 `offline_dataset: harvest_single` → 結果每跑必在 **HFSS 開始前**卡死（`prepare_models` 退到 `elif` 在 **24189 筆**上從零 `train_by_datas`，看起來像 HFSS 不動，其實是離線預訓練）。症狀正是「HFSS 沒開始收集資料就卡住、single_base 正常」。`pre_load_model` 預設仍 `strict=True`（其他實驗零影響）。測試：`test_pre_load_partial_warm_starts_rad_sm`、`test_prepare_sm_pretrained_rad_partial`。
- **訓練機制提醒**：訓 G 那步**不更新 SM**（兩個 optimizer 交替）。SM 只在 train_one_data/train_one_data_rad（真實 HFSS 監督）更新。
