2026-08-03 的 diffsim session（一整天）盤點出**我自己的失敗模式**，按結構分類。
這比任何單一技術結論都更能預測下一次會怎麼錯。

**Why:** 六類裡有三類是**重複發生**的（2/4/5 次），而且第①類我在第一次犯完之後
**已經把教訓寫進文件了，還是又犯一次**。⇒ 寫下教訓 ≠ 改變行為，必須改**流程**。

**How to apply:**

① **排除法只能排除你想到的**（2 次，都是「根因」等級）。我列了四條「獨立證據」
   宣稱排除所有可能，四條至今都成立，**結論卻錯了**——真正的候選我根本沒列進去。
   ⇒ 宣稱找到根因前，**先問「有沒有我沒列進候選的東西」**，並派一個 agent 專門找它。

② **宣稱修好但只落地一半**（4 次）。共同結構：**設定散在呼叫端 ⇒ 研究腳本與出貨路徑悄悄分岔**。
   ⇒ 設定要有**單一登記表**（`l2.SOLVERS` 的做法）；測試要**掃過登記表全部**，
   只守一個預設＝再犯同樣的病。

③ **指標漲但用途沒漲**（5 次）。修真 bug 讓 ρ +124% 而選批 P(勝隨機) 18%→17%。
   ⚠ 2026-08-03 出現**反向**的一次：絕對準度全面變差、選批卻翻 2.7 倍。
   ⇒ **驗收指標一定要用「使用方式」的指標**，ρ 只能當機制指標。

④ **我自己的資料/實驗錯誤，3 次全是 agent 抓到的、不是我**（共用 rng 導致樣本只 55% 交集／
   改到已經是實數的變數／閉式解取簡化式**兩次都讓落差看起來更大**）。
   ⇒ 每個「結論」跑完派一個 agent 複核，成本遠低於收回宣稱。

⑤ **工具與環境**（8 次）：MKL 多執行緒複數 LU 壞、路徑裡的 `\f` 變跳頁字元吃掉 25 分鐘計算、
   複數除零給 NaN 不是 inf、`max(cos,eps)` 讓積分在 t>π/2 爆掉。
   ⇒ 長計算**先存中間結果再分析**；路徑一律 `os.path.join`。

⑥ **紀律**：時間戳沒查 `date` 寫錯 3 次（見 [[feedback_check_clock]]）；
   一個 sub-agent 跑了全域 `taskkill`（我沒把共機公約放進它的 brief，是我的責任，
   見 [[feedback_shared_machine]]）。⇒ **每個 agent brief 都要含共機公約**。

**真的有效的只有五樣**（優先用它們）：
1. **無因次量當證據**——一次消掉整類干擾（不需 `Z_c`、不需擬合），結論才是硬的。
2. **儀器先自證**——新量測工具先用**不經過被測系統**的路徑驗（餵合成訊號看能不能還原）。
3. **跨實作對帳**——agent 獨立寫的另一支求解器給同一個數字。
4. **判準發車前寫死 + 配對 bootstrap**。
5. **不變式**（如能量守恆 η）——它抓到的 bug，主曲線看起來完全正常。
